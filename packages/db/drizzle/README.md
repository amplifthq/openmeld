# OpenMeld D1 Migration Runbook

`packages/db/drizzle` is the committed migration history for the current shared
Cloudflare D1 binding `OPENMELD_DB`.

## Source Of Truth

- Schema source: `packages/db/src/schema.ts`
- Drizzle config: `packages/db/drizzle.config.ts`
- Migration directory: `packages/db/drizzle`
- Production migration ledger: Cloudflare D1 table `d1_migrations`

Auth, Core, Runtime, Dispatch, and Diagnostics currently share the physical
`OPENMELD_DB` binding. Logical ownership is still domain-specific; physical sharing
does not make this directory a place for ad hoc cross-domain writes.

## Greenfield Baseline

OpenMeld starts with a greenfield D1 baseline:

```text
packages/db/drizzle/0000_openmeld_initial_schema.sql
```

This baseline was squashed before any OpenMeld production D1 database applied
the inherited ATS migration history. It is the first migration history for the
new OpenMeld product line, not a rewrite of an already-applied OpenMeld
production database.

Drizzle snapshots live under `packages/db/drizzle/meta/*_snapshot.json`.
They are generated by `drizzle-kit generate` through `pnpm db:generate`; they
are not manually maintained during normal work.

Each snapshot records the schema state Drizzle uses to compare the previous
schema with the current TypeScript schema and produce the next SQL migration.
`meta/_journal.json` records the ordered migration entries.

## Production Safety Rules

Do not rename, delete, reorder, squash, or rewrite a migration file that may
already be recorded in production `d1_migrations`.

Cloudflare D1 decides whether a migration is pending from the file name and the
production migration ledger. Rewriting history can make production treat an old
schema change as new work.

After the first OpenMeld D1 apply, this greenfield baseline becomes immutable in
the same way any production migration is immutable. Future schema changes must
append new migration files.

The normal production entrypoint is:

```sh
pnpm run db:release:prod
```

It fails unless the worktree starts clean. It builds the Auth code-generation
dependency, runs `db:generate`, and stops before touching production if any
tracked or untracked file changes. It then runs the read-only migration
preflight, applies pending migrations, verifies the physical contract, and runs
plain `PRAGMA optimize` once.

The migration preflight still consists of:

```sh
pnpm db:check
pnpm -C services/auth exec wrangler --config wrangler.jsonc --env prod d1 migrations list OPENMELD_DB --remote
```

`db:migrate:prod`, `db:verify:prod`, and `db:optimize:prod` remain focused
diagnostic commands. Do not hand-compose them as a second release workflow.
Component-only Worker deploys do not run the database release.

## Future Changes

Future cleanup may add tests, documentation, read-only preflight checks, and
broader `db:verify` coverage. It must not change already-applied production
migration file names or SQL bodies.
